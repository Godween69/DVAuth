# Как устроен DV Auth

## Основные понятия

- **Приложение** (client): ваш сайт или сервис, которому DV Auth помогает. Объявляется в
  настройках (DVAUTH_CLIENTS) и узнаётся по своему секрету. Данные разных приложений не смешиваются.
- **Человек** (subject): стабильный идентификатор человека в приложении, любая строка до 128
  символов. Лучше использовать внутренний номер (например, id в вашей базе), а не логин: логин
  можно переименовать. DV Auth не знает ни имён, ни паролей, только этот идентификатор.
- **Второй фактор**: способ, которым человек подтверждает вход после пароля.
- **Талон** (ticket): одноразовый пропуск ко второму шагу. Выдаётся после верного пароля, живёт
  5 минут. Пять неверных кодов сжигают его.
- **Запрос подтверждения** (challenge): одна попытка подтвердить вход или привязку в чате. Его
  идентификатор попадает в QR-код. Живёт 3 минуты.

## Два слушателя

Сервис открывает два порта, и это принципиально.

**Внутренний порт** (по умолчанию 3011). API для ваших приложений. Каждый запрос подписан секретом
приложения (заголовок Authorization: Bearer ...). Этот порт нельзя выводить в интернет: слушайте
на 127.0.0.1 или на внутренней сети.

**Публичный порт** (по умолчанию 3010). Туда ходит только приложение чата с телефона человека.
Здесь три адреса и ничего больше: /health, /v1/chat/info и /v1/chat/confirm. Даже если прокси
настроен небрежно, внутренние адреса отсюда недоступны (там ответ 404).

## Что хранится

База PostgreSQL, таблицы из migrations/0001_init.sql:

- **totp**: секрет TOTP человека. Зашифрован ключом DVAUTH_TOTP_KEY (AES-256-GCM). Хранится номер
  последнего принятого шага: так один код нельзя применить дважды.
- **recovery_codes**: запасные коды. Только хеш SHA-256, открытого кода в базе нет.
- **chat_links**: какому аккаунту Matrix принадлежит человек. Одному аккаунту Matrix соответствует
  один человек внутри приложения.
- **tickets**: талоны входа.
- **challenges**: запросы подтверждения в чате.
- **attempts**: неудачные попытки, по ним считается блокировка перебора.
- **events**: журнал событий безопасности (вход начат, неверный код, привязка, сброс). Кодов и
  токенов в нём нет.

## Как идёт вход

1. Человек вводит в приложении логин и пароль. Приложение проверяет их само.
2. Приложение вызывает `POST /v1/login/begin` с идентификатором человека и его адресом.
   Если второго фактора нет, ответ `{"required": false}`: вход завершён как раньше.
3. Иначе ответ содержит талон и способы (`chat`, `totp`, `recovery`). Сессию приложение пока не
   открывает.
4. Человек подтверждает вход. Либо вводит код (`POST /v1/login/code`), либо запрашивает QR
   (`POST /v1/login/chat/start`) и приложение чата подтверждает его.
5. Приложение получает «подтверждено» вместе с идентификатором человека и только теперь открывает
   сессию. Талон при этом сгорает.

Если DV Auth недоступен, приложение должно отказать во входе, а не пропустить человека без
второго фактора. Это правило для интеграции, подробнее в docs/INTEGRATION.md.

## Карта кода

- src/main.js: запуск, соединение частей.
- src/config.js: чтение настроек из переменных окружения, проверки.
- src/app.js: два слушателя и таблицы адресов, проверка секрета приложения.
- src/http.js: маленький HTTP-каркас, разбор JSON, заголовки безопасности.
- src/service.js: вся логика второго фактора.
- src/totp.js: TOTP по RFC 6238 и ссылка для QR-кода аутентификатора.
- src/secrets.js: шифрование секретов, запасные коды.
- src/matrix.js: проверка личности через Matrix OpenID.
- src/migrate.js, src/migrate-cli.js: миграции базы.
